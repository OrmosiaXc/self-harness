# 技术类概要设计配置

当用户另有数据库设计文档、部署文档、运维文档和用户使用手册时，使用本配置。目标是形成从业务需求到技术实现、功能逻辑和接口边界的设计说明书，不用其他文档内容凑篇幅。

## 固定八章主线

1. 概述；
2. 需求分析；
3. 系统总体设计；
4. 数据资源体系设计；
5. 算法任务与计算体系设计；
6. 密码应用与软件供应链安全体系设计；
7. 系统概要设计；
8. 技术路线。

项目没有某一专项体系时，可在提纲确认阶段替换为适用的专项章节，但需求分析、系统总体设计、系统概要设计和技术选型边界不得缺失。

## 章节最低要求

### 概述

覆盖项目背景、目标、建设内容、现状、范围、系统边界、文档边界、参考依据、术语和与其他专项文档的关系。

### 需求分析

必须分为：

- 功能需求分析：按业务角色、业务场景、合同功能、平台功能和外部集成完整展开；
- 性能需求分析：覆盖实时接入、任务计算、调度、查询、存储一致性、可靠性、安全、扩展性、可维护性和可观测性。

未冻结的容量、并发、SLA、RTO、RPO 和响应时间使用 `TBD` 或“设计控制建议”，不得伪装为合同验收值。

### 系统总体设计

至少包含：

- 建设原则；
- 建设思路；
- 总体架构设计；
- 系统上下文、业务架构、功能架构、技术架构、数据架构、集成架构和安全架构；
- 业务流程；
- 数据流程；
- 可靠性与可观测性；
- 系统约束与风险控制。

架构必须按可验证的真实运行单元表达，不能把模块化单体虚构为微服务，也不能把目标平台写成已落地现状。

### 专项体系

专项体系承接跨多个模块的统一机制，例如数据资源、算法任务、密码应用、软件供应链、安全审计和外部接口。说明设计目标、分层、职责、协作、状态、异常、版本和追溯，不重复第 7 章的单模块细节。

### 系统概要设计

按全部功能点逐一展开。每个模块固定包含：

1. 模块概述；
2. 功能架构；
3. 功能逻辑；
4. 业务流程；
5. 技术实现；
6. 数据与接口；
7. 异常与边界。

“业务流程”描述系统如何处理业务，不写用户点击步骤；“技术实现”描述组件、服务、算法和数据协作，不写部署命令、主机、端口或生产配置。

### 技术路线

技术路线只描述当前技术、选型依据、适用范围、限制和变更控制。结尾使用以下三个子章节：

1. 技术选型依据与决策原则；
2. 技术选型适用范围与约束；
3. 技术组件引入与变更控制。

不得使用“详细设计目标技术”“待平台、前端和联调材料确认的技术”等内部状态作为正式章节标题。

## 数据库边界

概要设计可以描述：

- 业务数据分类；
- 数据架构；
- 关系数据、缓存、文件系统和对象存储的职责；
- 数据来源、流向、生命周期、质量和安全；
- 业务对象、文件和接口之间的关联。

以下内容只进入数据库设计文档：

- 概念、逻辑和物理数据模型；
- ER 图；
- 库表、字段、数据类型、默认值和空值规则；
- 主键、外键、索引、唯一性及其他约束；
- 数据字典、SQL、初始化脚本和迁移方案。

## 其他排除项

- 部署拓扑、主机、端口、安装命令、发布操作和环境配置；
- 运维值班、备份执行、监控操作、告警处置和故障手册；
- 页面点击、表单填写、查询操作和用户培训步骤；
- 合同金额、个人联系方式、真实口令、Token、密钥和内部敏感地址。

合同中的“云平台发布对接”仍保留为供应链功能模块，只写制品、审批、接口、状态和异常，不写部署操作。

## 追踪要求

- 合同功能只能增加设计细节，不能删除。
- 建立“合同/需求—体系—子系统—模块—接口—验证方式—章节”追踪关系。
- 项目有大量功能点时，先冻结功能覆盖清单，再生成提纲。
- 正式标题不显示内部证据状态；状态保留在台账和附录。

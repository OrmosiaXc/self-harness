# 可复用提示词库

只选择当前阶段所需提示词。方括号内容替换为项目变量。

## 1. 任务与约束提取

```text
你正在制作一份[汇报类型]PPT。请分析用户要求和现有材料，提取：
1. 汇报场景、受众、时长、页数；
2. 必须包含、必须删除、禁止出现、必须保持不变的内容；
3. 事实来源与待确认项；
4. 内容确认和风格确认方式；
5. 可编辑性、演讲者备注、交付目录和版本清理要求。

不要开始构建 PPTX。把结果写入制作任务和约束清单；只提出会显著改变结果且无法从材料推断的问题。
```

## 2. 文档与源码事实核对

```text
请以只读方式分析[资料路径/源码路径]，建立事实与证据台账。

对每个将进入 PPT 的结论，记录：
- 结论；
- 状态：已验证事实/文档陈述/源码现状/目标表达/待确认；
- 证据文件和定位；
- 输入、处理、输出；
- 参数、异常、质量控制和边界；
- 适合领导汇报的一句话表达。

源码必须核对实际入口、调用链和输出，不只依据 README、文件名或注释。没有证据的精度、性能和成效不得写成事实。
```

## 3. 逐页内容目录

```text
基于已确认的任务和事实台账，规划一份[页数范围]页的[汇报类型]PPT。

每页输出：
- 页码与章节；
- 页面标题；
- 一句核心结论；
- 页面可见内容；
- 证据来源或表达边界；
- 建议视觉；
- 演讲提示；
- 确认状态。

要求：
- 每页只回答一个主要问题；
- 章节页数与复杂度匹配；
- 面向[受众]，技术内容按“目的—流程—结果—边界”表达；
- 不生成 PPTX；
- 在文末列出需要用户确认的章节、页数、删改和风险口径。
```

## 4. 目录变更与页码重排

```text
用户对现有逐页目录提出了以下变化：[调整要求]。

请：
1. 建立旧要求到新要求的变更映射；
2. 只保留用户最新明确要求；
3. 重新平衡章节页数；
4. 更新所有后续页码、目录、页面标题和确认项；
5. 检查总页数是否仍在[页数范围]；
6. 标出被删除、合并、新增和改写的页面。

不要进入视觉设计或 PPTX 构建。
```

## 5. 视觉风格提案

```text
为已确认的逐页目录提出[数量]套适合[场景/受众]的视觉方向。

每套说明：
- 设计关键词；
- 主色、辅助色和状态色；
- 中文标题与正文字体；
- 画布和安全区；
- 标题、卡片、流程、表格、图表和页脚规则；
- 适合的代表页；
- 风险和适用边界。

优先保证严谨、可读、可编辑和投影效果。避免随意拼贴、过度装饰、低对比度、无意义图形和模板化 AI 标题装饰线。
```

## 6. 风格效果图

```text
根据已确认的视觉规范，为以下代表页生成高保真 PPT 风格效果图：[页面列表]。

效果图必须：
- 使用 16:9；
- 保持统一网格、配色、字体层级和页脚；
- 展示真实页面内容，不用 lorem ipsum；
- 不伪造数据结果；
- 不把系统截图改造成不存在的界面；
- 重点检查标题换行、文字密度、对齐、留白和图形含义。

这些图片只用于确认风格，不作为最终 PPT 页面。
```

## 7. 代码到领导表达

```text
请核对[代码模块]的真实处理逻辑，并把[页码范围]改写为领导和验收专家容易理解的内容。

每页优先表达：
1. 要解决的问题；
2. 输入如何被处理；
3. 采用了哪些关键算法或策略，以及各自的作用；
4. 形成什么结果或证据；
5. 有哪些质量控制和适用边界。

保留必要算法名，但不连续堆叠类名、函数名和参数。若当前 PPT 描述与代码不一致，列出差异并以代码事实和用户最新要求为准。不要使用“领导关注”等对象标签。
```

## 8. 可编辑 PPTX 构建

```text
根据已确认的逐页目录和视觉规范，构建原生可编辑 PPTX。

要求：
- 16:9；
- 标题、正文、流程、卡片、矩阵、表格和图表使用 PowerPoint 原生对象；
- 截图仅作证据并可替换；
- 所有文本框启用 shrink 适配和固定边距；
- 登记对象坐标并检查画布边界、页脚保护区和文字溢出候选；
- 每页包含演讲者备注；
- 不使用整页效果图或整页截图替代可编辑页面；
- 构建工程保留 sources、notes、images、resources、scripts、exports、analysis 和 qa_render。

先生成到新版本目录，不覆盖正式旧版。
```

## 9. 独立视觉 QA

```text
请独立检查以下 PPT 渲染图片。假定存在问题，不要只确认“看起来正常”。

逐页检查：
- 重叠、遮挡、截断、拆词和超框；
- 页脚碰撞、贴边和安全区不足；
- 间距、基线和列宽不一致；
- 对比度和投影可读性；
- 图表单位、标签和图例；
- 箭头或流程方向不清；
- 图示是否容易被误解为真实结果；
- 页面是否过密、空洞或与相邻页重复；
- 占位符和禁用措辞。

对每页列出问题、严重度、证据和建议修复。即使问题轻微也要记录。
```

## 10. 修复与复验

```text
根据视觉 QA 报告修复[页码]，保留已确认内容和视觉体系。

要求：
- 先说明问题根因；
- 只修改必要对象；
- 检查修复是否引入新的换行、错位或相邻页不一致；
- 重新构建并渲染受影响页；
- 再执行全稿结构验证；
- 更新视觉 QA 报告，记录“问题—修复—复验结果”。
```

## 11. 交付与旧版清理

```text
发布[新版本号]前，请先核对：
- PPTX 存在且可打开；
- 页数、标题和备注数量正确；
- 构建脚本、资源、内容目录、验证报告和渲染结果齐全；
- SHA-256 已记录；
- 正式目录中的新文件名与构建状态一致。

仅当以上检查通过且用户明确要求清理时，删除以下被替代对象：[精确旧版路径列表]。
删除后重新列目录并更新交付说明。不要使用宽泛通配符，不删除未列出的文件。
```

## 12. 技术大纲与章节拆分

```text
基于制作任务和事实台账，先构建[汇报名称]的技术大纲，不生成效果图或 PPTX。

请输出：
1. 总体业务目标、技术主线和预期结论；
2. 章节 ID、章节目标、输入资料、输出结论和依赖；
3. 稳定页面 ID 和章节内顺序；
4. 父任务保留的封面、目录、过渡、跨章节页和总结页；
5. 可并行章节和必须串行的依赖；
6. 页面标题映射初稿。

章节边界必须允许每个子章节建立独立资料、证据、内容锁、效果图、构建和 QA。不要为了并行强行拆开存在强依赖的页面。
```

## 13. 全局构建契约

```text
为已确认的技术大纲建立全局构建契约，供父任务统一下发。

必须明确：
- 画布、安全区、标题区、内容区和页脚区的英寸坐标与所有者；
- 中文/英文字体、回退字体和字号层级；
- 主色、辅助色、强调色、状态色及其语义；
- 网格、间距、卡片、流程、架构、表格、图表和图标规则；
- CyberPPT 效果图、PptxGenJS 重建、备注、渲染和 QA 规则；
- 父任务与子章节的读写边界；
- 契约版本、哈希和偏差审批方式。

当前模式为[full-slide/content-only-integration]。若为内容页集成模式，标题区必须保留为空，子章节不得写标题、页码或全局页眉页脚。
```

## 14. 子章节任务下发

```text
你负责[章节名称]，章节 ID 为[章节 ID]，页面 ID 为[页面列表]。

只读取：[绝对输入路径列表]
只写入：[章节独立目录]
全局构建契约：[路径、版本、哈希]
页面标题映射：[路径]

执行顺序：
1. 建立本章节资料索引和事实台账；
2. 生成逐页内容锁；
3. 用 CyberPPT 生成整套效果图；
4. 效果图确认后建立组件签名和视觉元素登记；
5. 用 PptxGenJS 按页重建可编辑内容；
6. 执行结构检查、标题保留区检查、渲染对照和修复复验；
7. 提交子章节交付清单。

必须继承全局字体、色板、网格、组件和区域；不得修改父任务、其他章节、最终页码、全局标题或页脚；不得再次拆分任务。发现冲突时提交偏差申请。
```

## 15. 父任务集成与回归

```text
接收以下子章节交付：[章节和路径列表]。

先验证契约版本、页面 ID、内容锁、效果图、可编辑性、标题保留区和章节 QA。未通过的章节退回原任务，不在集成阶段临时重排。

对通过的章节：
1. 按页面标题映射排序；
2. 保留原生对象和演讲者备注；
3. 添加统一标题、章节标识、页码和全局页眉页脚；
4. 不使用截图、栅格化或整页缩放；
5. 执行页数、标题、备注、边界、字体、色板、网格、术语和密度检查；
6. 渲染 PDF、逐页 PNG 和总览图；
7. 完成至少一次修复复验并输出父任务集成验收报告。
```

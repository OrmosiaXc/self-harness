# AGENTS.md

## 项目目标

维护一个用于策划、生成、并行开发、集成、评审、修订和交付专业可编辑 PPT 的 Agent。它面向项目验收、领导汇报、技术评审、建设成果汇报等正式场景，强调事实可追溯、表达可理解、页面可编辑、章节可独立开发和交付可验证。

普通使用者只操作 `workspaces/<PPT名称>/` 下的任务、资料投递、确认记录、调整意见和成果目录。

## Startup Workflow / Agent 工程启动流程

当任务是维护本 Agent，而不是制作某一份 PPT 时：

1. 依次读取 `feature_list.json`、`progress.md` 和 `session-handoff.md`。
2. 运行 `./init.sh` 建立验证基线。
3. 同一时间只推进一个功能；修改后记录决策、风险和验证证据。
4. 结束前运行 `./init.sh --full`，同步更新状态文件和交接信息。

## PPT Runtime Workflow / PPT 任务启动流程

当用户要求生成、修改、重构、评审或交付 PPT 时：

1. 完整读取 `skills/create-professional-ppt/SKILL.md`。
2. 读取当前工作区的 `00-任务说明/制作任务.md`、`当前状态.md`、`长任务计划.md` 和 `会话交接.md`。
3. 读取 `02-资料识别/事实与证据台账.md`、`03-内容规划/技术大纲.md`、`00-任务说明/全局构建契约.yaml` 和父任务调度台账，只按当前阶段加载 Skill 引用的参考文件。
4. 从磁盘状态继续，不依赖聊天记录恢复长任务。
5. 运行 `python3 agent.py new "<PPT名称>"` 新建项目；已有项目禁止覆盖。

## 关键工作原则

- 用户最新明确要求优先于历史目录、旧稿和通用建议。
- 先做资料与代码事实核对，再写页面结论；无证据的规模、性能、准确率和成效不得写成既定事实。
- 用户要求先确认目录或风格时，将其设为硬确认点；确认前不越级生成正式 PPTX。
- 新建正式 PPT 默认先用 CyberPPT 生成整套效果图并确认，再用 PptxGenJS 重建可编辑 PPTX；效果图不是最终页面素材。
- 技术长篇先形成技术大纲、稳定页面 ID 和全局构建契约，再决定是否按子章节拆任务。
- 只有用户明确要求任务会话拆分或项目配置启用 `parallel_chapters` 时才创建独立任务会话。
- 父任务拥有技术大纲、共享样式、字体、标题映射、最终页码、全局页眉页脚、集成和全稿 QA；子章节只拥有自己的资料、内容锁、效果图、可编辑内容对象和章节 QA。
- 子章节使用扁平单层任务，不再次拆分；不同任务只通过父任务和磁盘状态同步。
- `content-only-integration` 模式必须保留空白标题区，只构建内容区；不得删除标题后扩大正文，也不得写入页码和全局页眉页脚。
- 面向领导汇报时使用“目的—流程—结果—边界”的顺序，算法名和代码名只作为必要依据，不让页面退化为源码说明。
- 架构、流程、矩阵、时间线、图表和文字优先使用 PowerPoint 原生对象，截图只承担证据作用。
- 不能把效果图整页贴进 PPT 冒充可编辑页面；不能把没有真实数据支撑的曲线或分类色彩表述成真实结果。
- 所有文本框必须启用缩小适配并保留安全边距；正文不得侵入页脚保护区。
- 生成后必须渲染为 PDF 和逐页图片，至少完成一次“发现问题—修复—复验”闭环。
- 有条件时由未参与构建的独立审阅者检查视觉问题；不能只检查源代码或 PPTX 能否打开。
- 用户要求删除旧版时，先复制并验证新版本，再只删除已明确被替代的旧 PPT、旧渲染结果和旧工程。不得先删后验。

## Parent-child orchestration / 父任务与子章节编排

- 父任务先锁定 `全局构建契约.yaml`，写入版本或哈希，再下发自包含子章节任务包。
- 子章节在 `05-构建工程/chapters/<chapter-id>/` 建立独立资料、证据、内容、效果图、构建、QA 和交付目录。
- 子章节不得修改父任务文件、其他章节或全局契约；确需偏差时提交父任务审批。
- 并行只发生在章节之间；每个章节内部仍按页顺序执行“内容锁—效果图—可编辑重建—渲染复验”。
- 父任务只接收契约一致且章节 QA 通过的交付，再统一写标题、页码和全局元素并完成全稿回归。

## One feature at a time / 单功能推进规则

- 维护 Agent 工程时，一次只推进 `feature_list.json` 中一个未完成或 `in-progress` 功能。
- 当前功能完成验证并记录证据后，才能关闭或切换。
- PPT 长任务的父任务同一时间只保留一个全局阶段；章节构建阶段可有多个独立活动子任务，每个任务必须有自己的状态和安全重启点。

## 资料和源码边界

- 外部合同、报告、PPT、图片和源码目录默认只读。
- 不在用户源码目录中写入分析报告、缓存、图片或构建结果。
- 区分合同事实、文档陈述、源码现状、目标表达和待确认项。
- README、注释和界面文案不能替代实际代码路径、输出文件或测试证据。
- 项目特有事实保存在项目工作区，不写入通用 Skill 和共享模板。

## Stay in scope / 范围控制

- 当前范围由 `制作任务.md`、资料索引、确认记录和用户最新要求共同限定。
- 局部改页时只修改受影响页及必要的目录、备注、验证脚本和版本说明。
- 未经授权不发送外部消息，不修改源系统，不覆盖原始资料，不删除未明确废弃的成果。

## 验证命令

```bash
python3 agent.py validate-agent
python3 skills/create-professional-ppt/scripts/run_smoke_test.py
./init.sh --full
```

对实际 PPT 工程还需执行：

```bash
python3 skills/create-professional-ppt/scripts/validate_editable_pptx.py --help
```

并按项目构建脚本完成 PPTX → PDF → 逐页 PNG → 总览图的完整渲染。

## Definition of Done / 完成定义

只有同时满足以下条件才能宣称 PPT 交付完成：

1. 页数、章节、逐页标题和用户增删要求与最终确认记录一致。
2. 关键结论均可追溯到文档、代码、数据、测试或明确的用户确认。
3. 页面表达符合目标受众，不含无依据指标、伪造图表、占位符、禁用措辞或不应出现的单位信息。
4. PPTX 的文本、形状、图表和流程主体可编辑，无整页栅格化替代。
5. 页数、备注、标题、文本适配、对象边界、页脚保护区和禁止项结构检查通过。
6. 全部页面完成渲染和视觉检查，并至少完成一次修复复验。
7. 构建脚本、资源、内容目录、验证报告、渲染结果和版本说明均可从交付目录恢复。
8. 如执行旧版清理，新版已先完成文件存在性、页数、哈希或结构复核，删除目标有明确记录。
9. 使用子章节并行模式时，技术大纲、全局契约、任务包、标题映射、章节交付和父任务集成验收均齐全。
10. 使用标题留白模式时，子章节页面标题区无可见对象，合并后标题和内容无碰撞。

## End of Session / 会话结束流程

1. 更新当前 PPT 工作区的状态、计划、确认记录、调整记录和会话交接。
2. 若维护 Agent 工程，更新 `feature_list.json`、`progress.md` 和 `session-handoff.md`。
3. 记录已执行的验证命令、实际结果、未解决问题和安全重启步骤。
4. 确保目录处于 clean、restartable 状态，下一次会话可从磁盘状态继续。
5. 在交接文件中写明 Next steps，不把必要状态只留在聊天中。

# 进度与证据

## 状态

任务状态与当前动作分开维护：动作只表示正在进行哪类工作，不表示完成程度。

| 任务状态 | 含义 |
| --- | --- |
| 待启动 | 仅规划，尚未开始实际处理 |
| 进行中 | 正在澄清或实施，验收尚未全部满足 |
| 待验证 | 当前实现已落地，相关验收点尚待验证 |
| 待确认 | 当前版本全部验收点通过，待用户确认任务完成 |
| 已完成 | 普通模式验收通过且用户确认；强制模式用户明确强制完成#，按实际交付结项并保留跳过项 |
| 阻塞 | 缺少必要决策或外部条件，记录阻塞原因和恢复条件 |
| 已取消 | 用户明确取消，保留记录但不计入有效任务总数 |

任务状态可回退。例如测试失败回到“进行中”，实现修改后回到“待验证”；已完成任务发生范围变化时重新打开，清除旧完成确认并注明原因。动作仍由用户触发，不因状态变化自动切换。

验收点状态为：未验证 / 通过 / 失败 / 阻塞 / 待复验。每条结果标注需求版本、实现版本、验证时间和证据。初始版本为 R0、I0，表示未形成基线；实质需求更新递增 R，交付物实质修改递增 I。纯进度记录更新不递增版本。

版本是任务内的本地记录编号，不替代 Git 提交或其他产物版本。验证时同时记录可用的提交号、文件版本或环境标识。变更影响的验收点标待复验；沿用未受影响结论时注明理由，不简单清空或机械复跑全部结果。

## 阶段与项目进度

阶段状态为：待启动 / 进行中 / 阻塞 / 待确认 / 已完成 / 已跳过。

- 阶段内开始实际任务后进入进行中；整体无法推进才标阻塞，局部任务受阻应在摘要注明。
- 所有有效任务已完成且阶段退出条件有证据满足后，阶段进入待确认；用户确认阶段完成后才标已完成。
- 已跳过必须有用户决定及原因，不伪装为完成。
- 阶段进度用“已完成任务数 / 有效任务总数”，已取消任务不计入分母。它只表示任务数量占比，不表示工时或真实工作量完成比例。
- 项目进度列出阶段状态与各阶段任务数量；总计排除已跳过阶段及已取消任务。分母随范围调整改变时注明原因。
- 不用各动作等权计算进度；一个动作可能重复多轮。
- 普通模式没有验收点、证据或用户完成确认时，不标已完成；强制完成#显式豁免未完成验证和功能门槛，按收尾规则如实登记；用户接受风险但某验收未通过时记录决定，并先明确调整范围或验收标准，不能篡改原测试结果。

## 同步顺序

每次动作收尾依次更新：

1. 仅在有效单动作触发后，按动作规则维护记录：测试复用 `测试/测试记录.md` 并追加概要，其他动作新增对应目录的一张卡片；再更新当前任务 `任务.md` 的摘要、循环日志、状态、完成确认和下一步。需求与验收定义来自最新有效澄清卡片；验证依据来自单份测试记录中的环境/版本、方法/脚本入口和概要结论，不要求完整运行输出附件。旧卡片保留，任务总览引用当前有效卡片及结果，不重复复制正文。
2. 当前阶段 `阶段进度.md`：任务表、完成计数、阶段退出条件、阻塞与建议。
3. harness 根目录下的 `项目管理/项目进度.md`：当前阶段/任务/动作、阶段汇总、总计和最近变更。

测试仅保留可复用方式/脚本和单份概要记录；原始输出不默认归档。其他动作的具体证据按其规则保留，上层只写摘要和链接。新增/取消任务、跳过阶段或重开任务后也同步计数。不同时维护多份内容完全相同的日志。

测试运行概要在单份测试记录中按时间追加，其他动作过程日志按其规则维护，结果表展示最新有效状态；更正错误时写明更正原因，不抹去失败历史。中断后若汇总不一致，核对任务证据并重算摘要。

## 知识与任务推进

任务总览记录知识状态（未触发 / 已沉淀 / 待补充）并链接相关知识卡片；知识卡片是否经过验证单独标注，不混入功能验收结果或完成计数。

允许启动并行任务，无需其他任务先完成。每个任务只有满足自身验收并获得用户确认后才能标已完成；知识完成或验证通过不能代替该确认。

普通聊天不执行以上写入。只有有效动作触发可新增一张动作卡片并同步进度；新任务#与用户完成确认只维护任务总览、阶段和项目元数据，不写动作或知识卡片。普通补充不能自动恢复上次动作的写入授权。需求#与方案#按本文末尾的专门规则维护阶段卡片及必要关联信息，不属于最小任务单元的动作卡。

# 阶段组织与任务拆分

| 阶段 | 聚焦内容 | 常见交付 |
| --- | --- | --- |
| S01 需求与范围 | 做什么、为谁做、如何验收 | 范围、规则、验收清单 |
| S02 方案与设计 | 怎么实现、边界与取舍 | 设计、接口与数据约定 |
| S03 功能开发 | 小功能逐个落地 | 功能实现及局部验证证据 |

阶段是可裁剪的规划，不是三个强制串行审批门。用户可以选择阶段或回到先前阶段；允许跨阶段并行开展不同任务，各自维护范围、依赖及完成确认。涉及依赖时先说明当前条件。不要因为前阶段完成就自行启动下一阶段。

每个阶段至少规划一个任务单元，真实项目可以增加多个。当前骨架每阶段只放一个首个规划任务，用于展示结构；开始使用时应按项目目标收敛范围。S03 按具体小功能继续拆分，不能让整个系统开发长期挤在一个单元。

任务应有单一可描述目标、清楚的输入输出与可独立观察的验收点。若包含互不依赖的目标或不能以最小验证判断结果，提出拆分建议，由用户确定范围。

每个阶段的任务均可按需使用任务动作与知识沉淀；项目分析可独立触发。阶段名称不限制动作：需求阶段可执行文档编写，设计阶段可测试接口约定一致性，开发阶段可验证实际功能行为。

阶段退出条件写在阶段说明中，实际满足情况写在阶段进度中。遇到技术设计文档任务时，遵循用户指定模板与项目适用的设计文档规则；本 harness 的目录结构不替代正文结构要求。

每个任务初始只使用任务.md 模板，动作目录按有效“提示词#”指令触发创建；知识由知识#或知识记录#触发，保存到根目录知识/任务分析，任务内只保留链接。新增小功能通过新任务#办理，遵循动作路由规则，不能借拆分或跨阶段安排绕过完成确认。

调研卡在启动和经用户触发的子会话反馈时维护同一份记录；主会话接收匹配反馈可更新原卡及进度，不视为新动作卡。调研结果不等于实现验收证据，不代替本任务完成确认。

默认开启或恢复任务时，先只读核对任务.md 的待完成功能点与设计记录，不隐式创建目录或记录。有效动作收尾时同步功能点状态、最新设计摘要及来源卡片链接，避免任务入口长期失真。

分析#指定项目目录属于项目级知识动作，成果只写入根目录知识/项目分析；无活动任务也可使用，不创建任务，不自动更新任务完成状态。分析与知识记录均一次一张正文卡。

## 任务恢复摘要

使用任务.md 的“任务恢复摘要”整合原当前进度与有效结论，不另建恢复文件。保留已完成内容、当前需求/实现版本、代码现场、最近有效验证及证据、待复验项、阻塞与恢复条件、调研分支、必要卡片链接和下一步建议。控制篇幅，不重复设计或卡片全文。

有效动作完成、匹配的调研反馈归档或完成确认后，更新相应变化。普通聊天、打开或恢复任务只读检查；仅接续时先核对有效摘要和路径；进入实施、验收或成果复用时核对实际仓库、分支/提交、相关未提交修改及验证版本。摘要和实际文件不一致时先说明差异，不自动执行、重测或标记成功。同一轮中断恢复使用摘要中的触发标识和卡片信息，避免重复记录。

## 需求基线

项目当前有效需求集中在 harness 根目录 `项目管理/需求基线.md`。任务记录本次关联的 REQ 编号、参考 B 版本、候选变更和确认依据；保持需求—功能点—验收之间可追溯，不复制整份基线。

首次在澄清#中取得明确确认后可建立基线。后续需求差异先留在任务；用户确认任务完成时，同步已明确确认的新增/修改/废止，记录来源任务及确认依据。歧义尚未解决时先澄清取舍，不凭完成一句话猜测。若只改变实现、不改变可观察需求，基线正文及 B 版本不变。

基线 B 版本仅在实质需求变化时递增；任务 R/I 保留各自含义。状态更新可回写实现与验证情况，但必须附证据且不能篡改需求。废止保留历史，不复用编号。同一同步重试先查来源任务、需求版本和已有变更，不能重复登记。详见基线文件内维护说明。

同步完成条件：任务的基线同步状态已写明结果或无需更新；需求有变化时基线、任务引用与项目摘要一致。中断时先核对这些控制信息，不重复完成确认或生成卡片。

## 新增阶段的最小结构

只有用户决定新增阶段时才建立 `阶段/Sxx-阶段名称/`，并同步项目进度。无需另存阶段模板。

- 阶段说明.md：编号、目标与边界、输入和依赖、预期产物、可核验退出条件，以及动作和知识沉淀在本阶段的用途。
- 阶段进度.md：阶段状态、当前任务、完成/有效任务计数、任务链接、退出条件证据、阻塞与下一步、用户完成确认。
- 任务目录：S03直接在 `阶段/S03-功能开发/S03-T编号-任务名称/` 建立，取消中间“任务”目录；S01/S02既有规划任务按原层级定位。使用 [任务模板](../assets/任务模板.md) 生成任务.md，初始化填写功能点、验收口径和已知设计摘要，并按目标位置重算链接；不预建动作目录或填入通过结果。

阶段说明链接到阶段进度，阶段进度链接实际任务。澄清、执行、测试、调研目录仍按触发创建，知识仍归根目录知识分类保存。

## 随手收集与后续关联

吸收 GSD“先捕获、后处理”的机制，新增需求#、方案#提示词；产物直接放入已有阶段目录，不建立“需求”“方案”子目录，不移植外部框架。

### 需求#：随手收集

在任何阶段输入需求#及想法内容，将本次内容收为 `阶段/S01-需求与范围/IDEA-001-主题.md`。第一次真实触发才生成卡片，不预建文件或业务示例。仅写需求#时，可用当前会话中唯一明确的待收集想法；没有内容或对象有歧义才询问。记录时不追问完整方案、验收清单或技术细节。

一张卡保留：IDEA 编号、标题、用户原意、时间、触发标识、来源任务或会话（没有则注明）、状态、待明确事项，以及方案/开发任务链接（初始可为空）。一次消息有多个零散点，先在同一张卡保留原意，后续按用户选定范围再拆分，不批量建卡。

状态使用“待处理 / 已有方案 / 开发中 / 已完成 / 暂缓 / 取消”。状态需有实际关联或用户决定支持；方案存在不代表需求已确认或已实现。卡片不计入阶段任务完成率，收集不自动重开已经完成的阶段。

用户用需求#明确补充已有 IDEA 时更新原卡并简记变更；否则新建一张。编号按 S01 现有 IDEA 最大序号加一，不复用取消编号；重试复用同轮触发标识对应的卡片。普通聊天、仅提到目录或没有有效“提示词#”指令的补充不延续写入授权。

### 方案#：按需完善

编制方法遵循 [需求规格与方案编制](需求规格与方案编制.md)，使用 [Spec方案模板](../assets/Spec方案模板.md)。Spec默认作为PLAN内的可验收规格，不新增独立Spec卡片或提示词。

输入方案#及 IDEA 编号或卡片链接，读取需求、适用基线和必要项目事实，在 `阶段/S02-方案与设计/PLAN-001-主题.md` 形成一张方案卡。上下文只有一个明确来源时可以省略编号；多个可能对象时先确认，不猜测。没有来源需求时先说明缺少关联依据，等待用户选择已有卡或通过需求#收集，不代触发需求动作。

方案保留 PLAN 编号、时间、触发标识、来源 IDEA 链接与所依据的更新时间、目标和范围、方案及取舍、拟拆分的小功能及验收点、依赖与未决项、关联开发任务和状态。用户指定技术设计正文结构时遵循该结构，按实际范围控制篇幅。无法确定的信息标明待确认，不编造项目事实；必要的只读官方资料核实属于方案取证，独立研究会话按调研#规则触发。

状态使用“草稿 / 待确认 / 已确认 / 待复核 / 已取消”，只有用户明确认可方案才标已确认。用方案#指定已有 PLAN，或用户明确要求定向修改已唯一定位的现有方案时，更新原卡并记录版本及变化；初次生成方案按 S02 中 PLAN 最大序号加一新建；同轮重试不重复创建。不自动执行代码、验证或创建任务，不因产出方案而标记阶段完成。

方案形成后在来源 IDEA 回填链接。方案正文只保存于 PLAN 卡；已有 S02 任务可引用它，不能再复制一份正文到任务动作卡中。相关最小单元的澄清#、执行#、测试#、调研#仍按原规则触发。

### 串联到开发

需求#和方案#是阶段级记录动作，可在无活动任务或当前任务进行时使用；只编制本次阶段卡片并维护关联，不切换当前阶段/任务指针、不变更当前任务范围、不改变完成确认。它们不创建最小任务单元；另一个任务可通过新任务#并行启动，无需当前任务先完成。

用户使用新任务#选择 PLAN 中一个功能后，创建或复用对应任务，任务.md 记录 IDEA、PLAN 链接、采用的方案版本或更新时间、适用 REQ/B 版本及本次功能范围；原卡回填实际任务链接。不批量创建任务，不把待拆分建议写成已存在的链接。范围和方案尚未明确的部分标待澄清，不自动编码。

一项需求可关联多个方案或开发任务，一份公共方案可引用多个需求。只有需求全部约定范围都已验收并获用户完成确认，才把 IDEA 标为已完成。方案完成或一个功能任务完成不等于需求整体完成；取消或暂缓部分范围时保留用户决定。

IDEA 是候选收集编号，REQ 是正式基线编号。收集和方案编制都不自动更新 `项目管理/需求基线.md`，也不增加 B 版本；按既有确认规则进入基线时回填对应 REQ。需求补充影响已有方案时将关联 PLAN 标为待复核，在相关任务中提示影响，不自动重写实现或改变已确认任务范围；需按现有动作与确认流程处理。

示例：`需求#希望支持批量导出，先记下来` → S01 一张 IDEA；`方案#IDEA-001` → S02 一张 PLAN；用户明确启动后，`新任务#根据 PLAN-001 实现导出文件生成` → S03 一个最小任务单元。每一步分别由用户触发。

## 开发任务启动后的聊天接续

新任务#、任务#及【新任务】、【任务】遵循同一并行启动规则。建立或复用一个功能任务后，按 [开发任务分支与接续](开发任务分支与接续.md) 默认创建最小摘要接续聊天并登记；仅用户明确要求完整历史时fork；创建/发送失败保留任务及恢复信息，不重复建任务。聊天分支不增加业务任务数量，不改变验收状态。后续开发在子聊天维护同一任务。

## 任务完成#与强制完成#收尾

`任务完成#`与`强制完成#`是完成确认、结果回传和开发子会话归档的组合入口，按[任务完成与归档](任务完成与归档.md)执行。普通模式验收通过，或强制模式用户授权并核对实际交付后，业务状态可为已完成，回传或归档失败单独记录，不重复统计完成数。来源主会话接收登记后才归档子会话；普通完成确认不自动扩大为归档授权。

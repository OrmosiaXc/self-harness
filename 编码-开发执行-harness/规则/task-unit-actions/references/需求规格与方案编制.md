# 需求 → Spec → Plan 编制规则

## 适用范围与入口

用于本 harness 的需求收集、方案编制及指定方案修订。入口仍为 `需求#`、`方案#`，不新增 `spec#`，不要求安装外部 Spec 工具。不把示例中的数据库、框架、文件数量或具体项目路径写成通用要求。

- **IDEA** 保存用户意图、已知范围与未决项。
- **Spec** 是可核验的行为规格：在什么条件下，接受什么输入，产生什么结果，保持哪些约束。
- **Plan** 说明实现该规格需要改哪里、改什么、为何这样改、何时不改，以及如何验证。

默认将 Spec 和实现 Plan 放在同一张 S02 PLAN 卡中；Spec 是内容层次，不是必须新增的目录或文件。使用 [Spec方案模板](../assets/Spec方案模板.md)，按复杂度控制篇幅。已有用户指定的 Spec 文件时引用其路径、版本和条款，不复制维护第二份；未找到时明确“本 PLAN 内形成规格草案”，不能声称已读过某份规范。

编号、落盘、状态和与任务的关联遵循 [进度与阶段](进度与阶段.md#随手收集与后续关联)。本规则不自动启动开发、不修改业务代码、不执行外部写入或集成测试。

## 1. 需求收集：保持轻量

`需求#` 一次保存一张 IDEA。保留原始描述，并用已知信息说明目标/问题、涉及系统或使用者、预期行为、范围与已知约束。缺失信息列为未决项，不为填满模板编造需求，不要求用户先回答完整设计问卷。

区分用户明确要求、用户提供的现状、Agent 理解与建议。用户说“已完成”的前置工作可作为方案输入，但说明是否独立核验，避免再次安排已完成的工作。收集阶段不默认扫全仓、不选择完整技术路线、不生成 Plan 或正式 REQ 编号。

需求收集先轻量检索[成果索引](成果索引与复用.md)，把相关能力链接写入IDEA；不把候选能力直接当作已验证依赖。

## 2. 方案输入与证据核查

`方案#` 开始时定位来源 IDEA、所依据的更新时间、适用需求基线和本轮明确补充。对象明确则直接推进，不重复索取已提供的信息。核对项目上下文及相关代码版本；既有分析卡是线索，不代替当前代码证据。

方案编制先检索索引/任务完成结果和索引/调研结果，核对原方案、当前代码方法及验证版本，在修改清单记录复用或不适用依据；不重复实现已有基础能力。

按影响范围检查：

- 当前行为、模块/类/服务/接口调用关系、配置入口及其继承/覆盖顺序。
- 改动点的上游输入、下游结果消费、错误处理和状态变化；不能只检查匹配关键词的局部代码。
- 用户要求“全部检查”时列出真实扫描范围、文件/对象总数和排除项；关键字命中只用于定位，未命中不等于兼容通过。区分全局默认与局部声明，必要时核查实际有效配置。
- 涉及外部版本或兼容能力时，优先核查本地依赖及官方资料，记录版本与来源；资料支持不等于目标环境验证通过。必要的只读资料核实属于方案取证，独立研究会话仍由 `调研#` 发起。

证据表述分为：**用户确认事实、代码观察事实、目标环境实测、待验证假设、建议选择**。每个重要结论注明适用范围，不把潜在风险写成已经发生的故障。

缺少信息时继续完成不依赖该信息的部分；仅对影响方案分支的关键问题询问。把未知条件对改法的影响写清楚，而不是只写“待确认”。不得猜测容量、时延、吞吐、性能倍数或外部接口契约。

## 3. 形成可核验 Spec

在 PLAN 的需求分析部分，将需求转成可观察行为。使用 PLAN 内局部编号（如 F01、N01、AC01），明确它们不是正式需求基线的 REQ 编号。

每个核心功能至少描述：使用者/触发条件、输入与前置状态、处理规则、输出/后置状态、异常与边界、验收方式。兼容或重构类需求还应明确必须保持的接口、返回类型、状态语义和调用契约。

性能需求区分系统性、业务性和可扩展性。没有确认指标时写采样条件、对照方法与待确定阈值，不捏造承诺。小需求可用紧凑表格呈现，但不能只把用户原话改写成技术名词。

建立可追溯关系：**来源 IDEA/外部 Spec 条款 → 局部规格 → 设计与修改点 → 验收项**。每项实现建议须说明服务于哪条需求；无对应需求的优化放入可选建议，不混入必须实施范围。

## 4. 将 Spec 转成修改方案

### 修改清单

对必要修改给出文件/模块/接口位置、当前行为、拟调整内容、对调用链的影响、依赖和验收依据。新增组件标为“拟新增”，不要把拟建路径描述成已有文件。已有文件可附经核实的符号名或行号。

所有项区分：

| 分类 | 使用条件 | 写法要求 |
| --- | --- | --- |
| 必须修改 | 当前实现与确认目标存在明确差异 | 写清差异、证据及具体改法 |
| 条件修改 | 依赖实际配置、输入、版本或驱动等条件 | 写出触发条件、验证办法；通过则保留，失败才局部调整 |
| 保留并回归 | 暂无必须改动的依据，但属于影响链路 | 写出保持的契约及验收点，不预设重写 |
| 部署/验收事项 | 缓存、环境、发布等运行要求 | 与代码改造分开，不称为SQL/接口必须修改 |
| 可选优化 | 并非满足当前需求的必要条件 | 说明收益与代价，未经选择不纳入实施 |

必要时再区分语句/接口执行失败、业务结果差异、性能影响和纯流程要求。风险级别不等于修改确定性；“高风险待验证”不能自动变成“必改”。

### 设计与取舍

方案必须回答：为什么选择、在哪使用、何时不使用。只有存在实际选择时比较备选，不为凑模板虚构方案。优先沿用既有架构和业务契约，避免顺带改命名、升级框架、重构无关模块或重复执行用户已完成的前置工作。

条件性风险提供“验证通过保留 / 验证失败的最小修正”分支。影响共享配置时核对其他调用方；不要用全局开关解决尚未证实的局部问题。区分原有缺陷和本次变更引入的差异，发现前者先说明关联和范围，不能直接扩大任务。

### 验证与实施拆分

验证规格应列前置环境/数据、输入、预期结果、证据采集和适用边界。根据实际业务覆盖正常路径、异常、边界、事务/并发及结果消费；没有相关风险时不机械增加全部检查类别。静态扫描、模拟测试、真实环境测试分别标注，计划状态初始为“未验证”。

将工作拆成可独立描述和验收的小功能，说明依赖及顺序，只写拟拆分建议，不自动创建任务目录。用户随后通过新任务#或其别名选定功能时，按 [开发任务分支与接续](开发任务分支与接续.md) 建立一个任务并分支聊天。缺少运行环境不阻止形成方案草案，但必须说明哪些实施决策或验收尚不能确定。

## 5. 技术方案正文结构

用户最新目录或模板优先。默认核心正文依次为：

1. **需求分析**：功能需求分析、性能需求分析。
2. **系统总体设计**：建设原则、建设思路、总体架构设计、业务流程、数据流程，保持此顺序。
3. **具名体系设计**：按实际项目设置一个或多个体系；说明定位/目标、架构、模型/组成、流程、状态异常保障及模块边界，不能最终命名为空泛的“体系设计”。
4. **系统详细设计**：按系统域—子系统—模块展开，重要模块包含概述、功能架构、模块流程、模块接口、业务流程，并覆盖适用的输入输出、状态、异常、配置、权限、日志、并发、性能与验证。
5. **技术路线**：选择理由、适用位置、不适用边界。

章节编号随体系数量连续调整；小范围方案保留上述维度，用短段或表格表达，避免无内容的长模板。修改清单、验收与拆分纳入相应章节，详细检查表可作为同一卡片附录，不另造重复正文。

## 6. 方案复核与定向修订

- “检查方案是否遗漏”默认为只读评审：给出有证据的遗漏、实际影响和建议，不自动把所有建议写入方案。
- 用户明确指定已有方案并要求“把第1、3项补充进去”等，是对该文档的定向修改授权；上下文对象唯一时直接更新原 PLAN，不要求再输入一次 `方案#`。这不授权新建需求、开始开发或采纳其余建议。
- 实质性规格/设计变化递增 `spec_version`，更新时间并保留简短变更记录；纯文字或链接修正不必升级规格版本。来源需求版本记录为实际依据版本，不能为了对齐时间改写来源历史。
- 方案修订同步相关修改清单、验收和附录口径，避免正文新增检查范围但附录仍被误认为完整覆盖。仅更新受影响内容。
- 修订不等于用户确认方案：未确认保持草稿/待确认；已确认方案发生实质变化时标待复核。IDEA仅维护必要关联，已有活动任务受影响时按进度规则提示待复核，不自动变更需求基线或完成状态。

## 7. 交付前核对

确认来源及用户最新范围一致；已完成前置工作未被重复安排；需求到修改/验收可追溯；必改/条件改/回归/运维项分类准确；文件与符号可定位；未知项未伪装为事实；结构与编号完整；新增建议无越界；版本与链接一致。完成静态审阅不等于运行验收通过。

最终回复给出方案链接、主要决策、待验证条件以及实际完成范围。规则维护本身不生成业务 IDEA/PLAN，不改变既有方案，也不改变当前阶段或任务。QA按工作区的按需规则独立处理。

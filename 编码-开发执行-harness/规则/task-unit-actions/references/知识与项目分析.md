# 知识与项目分析

## 统一存储

`知识/` 位于 harness 根目录，与 `阶段/` 同级，包含 `项目分析/` 和 `任务分析/`。不要与被分析业务项目的根目录混淆，也不要再创建任务内的知识目录。一次触发生成一张 Markdown 卡片，编号与恢复规则见 SKILL.md。

## 知识# / 知识记录#

支持 `知识#`、`知识记录#`，可附明确主题。读取当前任务的任务.md、已有澄清/执行/测试/调研卡和相关会话内容，提炼一个有复用价值的主题，如业务规则、实现思路、问题原因、验证方法或开发经验。

单独触发而未指定主题时，根据当前任务最近的实际工作选取一个主要主题并明确说明；无任务或无可用材料时询问，不编造卡片。普通讨论可以成为素材，但只在本次有效触发后写入。

卡片写入 `知识/任务分析/Kxxxx-任务编号-主题.md`，包含：

- 来源任务编号、名称、任务.md 链接及需求/实现版本。
- 问题背景、核心结论、可复用步骤、适用条件与限制。
- 关联动作卡片及必要证据，区分已确认事实、已验证经验与待验证假设。
- 相对已有同主题知识的补充或修正，以及剩余问题。

在来源任务.md 中仅登记根目录知识卡片链接，不重复保存正文。知识卡片不是功能测试证据，不能将经验总结自动计为任务完成。已完成任务可以在用户明确指定后补充知识而不重开业务实现；不得因此切换活动任务。

## 分析#指定目录的项目

这是项目级的代码理解动作，可在项目开发开始前使用，无需先建立最小任务单元。例如：`分析#/绝对路径/业务项目 的项目，梳理模块、功能和类之间的关系`。

1. 确認目标路径：使用用户提供的路径，或其明确指向的已配置项目路径。路径缺失或多个候选不能唯一确定时先询问；无权限或路径不存在时说明阻塞，不分析另一个项目代替。
2. 只读勘察：先读适用的项目指令、目录、入口、构建或依赖声明，再按实际业务入口追踪模块。使用 rg 等精准搜索，排除依赖缓存、构建产物和无关大文件，不读取秘密配置值。
3. 梳理模块与功能：识别模块职责、核心功能、关键接口、外部依赖，以及模块之间的调用或数据关系。结合实际代码核对 README，不能只据目录名称猜测能力。
4. 梳理类与关系：覆盖关键业务类的职责、继承/实现、组合或依赖、关键方法调用、状态与数据流。区分静态引用、依赖注入、动态加载、事件订阅等关系；代码不能证明的运行时关系标为推断或待验证。无类的语言或项目用函数、组件、服务等实际单元表达，不虚构类。
5. 选择代表性业务链路：从入口到主要处理再到存储或外部调用，说明关键分支及异常路径。大型项目优先核心模块，明确已覆盖范围与未覆盖部分，不假称完整梳理整个仓库。
6. 写入一张 `知识/项目分析/Pxxxx-项目名-结构分析.md`。不修改业务代码、不安装依赖、不启动程序或测试、不自动开启调研子会话。

## 项目分析卡片内容

- **分析范围与代码快照**：目标绝对路径、项目名、分析日期、分支/提交号（可获得时）、未提交修改情况和未覆盖范围。没有 Git 信息就如实说明。
- **项目概况与入口**：实际技术栈、启动入口、模块划分与职责。
- **模块与功能关系**：用简洁表格说明模块、功能、输入输出、依赖与依据位置。
- **核心类或组件关系**：列出关键类/函数/组件、职责、继承与依赖、调用方向及证据位置。
- **关键业务链路与数据流**：描述入口、关键处理、数据读写及异常分支。
- **设计观察与待确认项**：区分事实、推断与建议；给出对后续开发有帮助的边界和风险，不把建议当作已采用设计。

关键关系须附代码文件路径及必要行号、符号名称；静态引用不能自动等同运行时必然调用。需要图示时可在同一卡片内用简短 Mermaid，不额外生成图文报告或第二张卡片。分析结果只证明所检查代码快照下的理解，不代表功能实测通过。

完成后返回卡片链接及关键发现，可在项目上下文登记此分析卡的路径；不改写当前任务状态或用户已确认的方案。再次分析形成新卡并引用前次分析，说明代码或认识变化。

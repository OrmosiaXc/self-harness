# 按章节职责写作

先明确本章要回答的问题、已确认下级目录、上下游边界、来源与缺口，再按事实组织正文。一个主要结论应有对象/问题、处理方法、协作边界、关键约束及可验证方式；根据章节用途选取，避免机械重复。

| 类型 | 内容重心 | 不能替代 |
|---|---|---|
| 方案 | 目标、范围、约束、可执行安排、判据、风险/回退 | 不能当作实际完成报告 |
| 技术设计 | 职责、模型、流程、状态异常、接口及选型理由 | 不能只列功能或源码文件 |
| 实施/测试报告 | 环境与版本、真实过程、证据、结果、问题和结论 | 不能用未来计划或预期结果代替实测 |
| 手册 | 角色与前提、操作输入、步骤、预期结果、失败处置 | 不能用架构介绍代替操作 |
| 台账/清单 | 稳定ID、对象、状态、责任/时间依据和闭环证据 | 不强制套多段论述 |

重要叶子小节如果只剩泛泛的一段话，应检查是否遗漏对象、机制或验证；可通过有意义的段落、表格或流程展开。内容深度按章节职责判断，不使用统一字数或段数门槛。术语定义、短约束、表格或步骤足以说明时允许简短。拒绝靠重复套话、增加空标题、重复同构表格凑篇幅。

正文用准确术语和可验证动词；区分“应”“拟”“已”。同一概念首次说明后保持一致。流程适合用图，固定字段比较适合用表；图表必须有上下文解释，不能仅粘贴截图或架构图。

性能未知时写清度量对象、设计机制、验证条件及待确认值，不能创造容量、时延、倍数或通过率。章节C更新同步来源、问题与追踪关系；正式报告的缺口不会因文字润色而变为通过。

# 资料分类、取证与证据措辞

## 分类与冲突

逐项判断材料用途：强制要求、项目事实、目录参考、内容参考、样式参考、正式模板、不使用、待确认。同一文件可有不同用途的段落，记录到相关索引/证据行。索引仅提供位置，必须读到支持结论的内容。

用户明确范围与当前项目批准需求决定“应该做什么”；源代码、配置结构和真实运行记录决定“已经实现/执行什么”。二者冲突时记录差异，不能用代码缺失删除有效需求，也不能用合同代替已实现证据。同类资料优先考虑版本、批准状态和适用范围；关键冲突影响设计方向时呈现选项等待澄清，其余缺口记录后继续独立工作。

| 主张类型 | 支持材料 | 表述与限制 |
|---|---|---|
| 合同/需求 | 有效条款或用户确认 | “应提供”“要求满足”；不等于已实现 |
| 静态实现 | 实际调用代码、接口、结构 | “代码中采用/实现”；不能证明生产部署、联调或性能 |
| 运行事实 | 指定环境/版本/日期的执行记录 | 描述该次结果及范围，不外推未测场景 |
| 目标设计 | 方案、设计稿 | “拟采用”“设计目标”；不写成现状 |
| 未确认 | 来源不全、冲突或假设 | 标待确认并说明影响；不编数值补齐 |

## 代码取证

先看项目构建、模块及入口，区分主应用、独立算法、未纳入构建的目录、第三方资源和示例。README、注释、测试代码与配置样例只作线索，沿实际调用路径交叉核对。

平台功能按入口→业务服务→数据准备→调用协议→处理状态→结果解析/归档→查询/权限/审计追踪；记录适用的失败、超时、重试、幂等和并发机制。Java/Python结合时核对双方输入参数、文件/消息格式、退出状态、结果解析及失败处理，不能只凭两边目录都存在就声称集成完成。

算法按入口、前置依赖、参数、处理步骤、窗口/阈值/模型、输出以及平台使用方式记录。目录名不能直接证明算法能力。前端缺失只能确认后端服务；截图经查看后可支持界面观察，不能单独证明后台处理正确。

内部证据定位至少含源ID、文件/符号或章节、提交/哈希/版本、观察结果和支持范围。已有相关结论复用前检查源版本。源码只读，所有分析、临时产物和缓存留在当前任务或临时目录，不记录密钥、口令等真实秘密值。

# 设计结构与模块展开

## 从要求到结构

核心顺序遵循harness：需求分析→系统总体设计→具名体系设计→系统详细设计→技术路线，封面/概述可在前。用户指定目录优先，源条款需映射到实际章节；不使用其他项目的固定章数或专项体系作为默认承诺。

需求分析同时覆盖功能和性能；功能按实际角色、场景、有效合同条款、现有能力和外部集成组织。性能区分系统性、业务性、可扩展性；未确认容量、时延、SLA等只记录验证对象和机制，不赋予硬性数值。

总体设计按建设原则、建设思路、总体架构设计、业务流程、数据流程展开。架构应说明系统边界、逻辑层、应用功能、技术关系及真实运行单元。Java多个模块不自动等于多个服务，算法目录不自动等于独立部署单元；目标平台不能写成既有部署。

具名体系承接跨模块共同机制，按项目选择，说明目标、架构、模型、流程、状态异常、保障和边界。模块章节只展开自身职责，避免重复整套体系。

## 模块内容映射

遵循当前五项模块结构；模块覆盖维度作为内容检查，嵌入对应位置，不再追加一套重复标题。

| 当前模块结构 | 应覆盖的设计内容 |
|---|---|
| 概述 | 目标、职责、包含/不包含和对应需求 |
| 功能架构 | 内部能力、上下游依赖、组件/服务/算法及权限边界 |
| 模块流程 | 规则、输入处理输出、状态、并发、异常、超时、重试/补偿及幂等（按实际适用） |
| 模块接口 | 输入输出、协议/文件/消息、数据归属、兼容性、错误契约和实际证据 |
| 业务流程 | 参与者、业务活动、分支和结果；不以点击步骤代替设计流程 |

按需补配置、日志、性能与验证点。概设描述机制与边界，详细设计可落到必要类/字段/接口；代码标识仅在帮助读者理解或复核时出现，不输出源码文件清单代替设计。

## 专项边界

概要设计可以保留数据域、核心实体关系、存储职责、运行单元、安全与集成边界；物理字段、详细SQL、安装命令及运维操作按用户范围放入专项文档或附件。存在相关需求但未安排独立文档时，在大纲阶段明确承接位置，不能因为源Agent的默认排除项而删除需求，也不能自动创建新文档。

技术路线逐项回答为什么选、在哪里用、何时不适用，并说明约束、替代条件和变更影响。实际依赖版本按证据写；读取依赖文件不等于确认现场版本。

## 完成检查

要求是否有章节与验证映射；边界/术语/图文是否一致；主流程、数据流程是否各自完整；体系与模块是否重复；模块输入输出和异常是否足够支持后续工作；结论是否超出证据；技术路线是否只有产品名而无理由。缺失项写成可定位问题而非空泛评分。
